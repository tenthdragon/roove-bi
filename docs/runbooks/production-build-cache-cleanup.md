# Production build-cache maintenance

`roove-bi-build-cache-cleanup.timer` runs hourly at minute 15 in Asia/Jakarta,
with up to five minutes of random delay and one minute of timer accuracy.
`Persistent=true` catches up after the server was off. The service is independent
of the app release and does not restart the application or sync workers.

Only real directories named `.next/cache/webpack` directly inside recognized
Roove BI releases under `/var/www/releases/roove-bi` are eligible. Every cache
file/directory must be unchanged for at least 24 hours (mtime and ctime).
The cleaner always protects:

- Both `current` and `previous`, plus other release symlink targets.
- The three newest releases by build timestamp (release-directory timestamp if
  no build ID exists), including a newly prepared candidate.
- Any release with a running process whose working directory is inside it.
- Any target containing a symlink, mounted filesystem, nonregular file, or recent write.

The cleaner does not remove release directories, dependencies, compiled server
or browser bundles, `.next/cache/fetch-cache`, environment files, databases,
Docker volumes, backups, or staging. Disk use outside webpack caches is outside
this job's scope. Cache files can be regenerated by a future build; their removal
does not remove the ability to run or roll back an old release.

A shared exclusive lock serializes cleanup with deployments. Missing/broken or
external current/previous links, unreadable process/cache inventories, and a link
change during a run abort cleanup. fd-relative deletion refuses symlink/ancestor
substitution. The systemd sandbox makes the active and rollback releases read-only
and permits writes only inside the production release root and the lock directory.

## Deployment coordination

The checked-in `deploy/digitalocean/deploy.sh` acquires the shared lock before
building. Every other production build, cutover and rollback helper must do so:

```sh
flock --exclusive /run/lock/roove-bi-release-maintenance.lock python3 /path/to/release-helper.py
```

Hold the lock for the whole operation, not just the symlink change. A timer run
that encounters the lock logs a skip and tries again at its next scheduled run.
Do not call the cleaner from inside a deployment expecting it to acquire the same
lock; run its dry-run separately. Do not run two ad hoc release helpers without
this coordination.

## Install or update

Use these files from an approved, CI-passing `main` commit. This is a maintenance
release; the running application commit/build and database remain unchanged.
Record the maintenance commit and installed file hashes separately.

```sh
install -d -m 755 /usr/local/lib/roove-bi-maintenance
install -m 644 deploy/digitalocean/cleanup_build_cache.py /usr/local/lib/roove-bi-maintenance/cleanup_build_cache.py
install -m 644 deploy/digitalocean/roove-bi-build-cache-cleanup.service /etc/systemd/system/
install -m 644 deploy/digitalocean/roove-bi-build-cache-cleanup.timer /etc/systemd/system/
systemd-analyze verify /etc/systemd/system/roove-bi-build-cache-cleanup.service /etc/systemd/system/roove-bi-build-cache-cleanup.timer
python3 /usr/local/lib/roove-bi-maintenance/cleanup_build_cache.py
systemctl daemon-reload
```

For an update, stop this timer, let any running cleanup finish, and hold the shared
lock while replacing the script/units. Keep a copy of the previous maintenance
files for rollback. Do not change existing application/worker/staging units.
Review the dry-run's eligible/protected release names before the first actual run:

```sh
systemctl start roove-bi-build-cache-cleanup.service
journalctl -u roove-bi-build-cache-cleanup.service -n 50 --no-pager
```

Each run logs structured JSON with protected releases, eligible/removed caches,
allocated-byte estimates and remaining free disk. `status=skipped` is normal during
a deployment; failures exit nonzero and appear in the service/journal. Validate
that application PID, current/previous links, protected caches and app health are
unchanged, and run again to verify idempotence. Then enable the schedule:

```sh
systemctl enable --now roove-bi-build-cache-cleanup.timer
systemctl list-timers roove-bi-build-cache-cleanup.timer --all --no-pager
```

Log retention is managed by the host journal, not this job.

To disable, `systemctl disable --now roove-bi-build-cache-cleanup.timer`; stop the
oneshot service too if currently running. To roll back the maintenance code,
disable the timer, restore the saved script/units under the shared lock, run
`systemctl daemon-reload`, then re-enable the timer. No database recovery or app
restart is involved.

Validation: `python3 -m unittest discover -s tests -p 'test_build_cache_cleanup.py' -v`.
CI runs these filesystem safety tests before the app checks. All tests use temp
directories; no production or local application data is used.
